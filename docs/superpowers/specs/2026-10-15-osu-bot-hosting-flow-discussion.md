# osu! Discord Bot：主持模式與操作流程討論紀錄

日期：2026-10-15
狀態：暫存討論，尚未定案；依使用者要求先保存，後續再討論。
關聯：[帳號、房間生命週期與權限設計](2026-10-15-osu-bot-lifecycle-permissions-design.md)

本文件記錄後續提出的需求方向與建議，不覆寫關聯文件。尤其 Bot 自動主持模式與原本「使用者主導、不處理圖池」的範圍不同，是否納入第一版尚待確認。技術選型、其他分支與實作計畫不在本輪討論範圍。

## 1. 兩種使用模式

### 模式一：Bot 主持，依序打圖

使用者描述的主線：

Discord 開房指令（房間大小、邀請名單）→ 建房並套用設定 → Bot 發送 !mp invite → 玩家進房 → 確認定位 → 雙方就位 → 依指定圖序進行。

- 使用者希望自動化主持，避免自己逐張選圖、設定與開始。
- 1v1、2v2、3v3 可依指令參數中的玩家順序分隊；例如 2v2 前兩位一隊、後兩位另一隊。此為目前建議，具體參數與 slot 規則待定。
- 圖池／圖序來源、每圖 mods、計分規則、勝負判定及是否納入評分池仍待討論；不因自動跑圖就視為全部納入。
- 「確認定位」目前理解為指定玩家到齊且隊伍／位置正確，精確定義待定。

### 模式二：Bot 建房，使用者主持

使用者描述的主線：

Discord 開房指令（房間大小、邀請名單）→ 建房並套用設定 → Bot 發送 !mp invite → 玩家進房 → 授予指定使用者 referee → 使用者自行打圖 → 關房 → Bot 發布圖池與 mp link 到頻道。

- referee 預設給下指令者，也希望可由指令指定授予對象。
- 指定 referee 是否同時移轉 Bot 房主權限尚未決定；兩者不可自行視為相同。
- 「發布圖池」究竟指預先提供的清單，或實際打過的圖及順序，尚未確認。
- !mp invite 是邀請進房；!mp addref 是授予裁判／管理權限，兩者不能互相替代。

## 2. 模式一：定位與準備倒數

### 使用者提出的方向

- 調整紅藍隊／位置時先放一個倒數計時器。
- 定位完成後設定第一張圖，再開準備倒數。
- 全員準備或倒數結束，任一條件成立就開始，不無限等待玩家準備。
- 每張圖結束後，預期繼續下一張圖與準備流程；詳細推進與結束條件待定。

### 指令依據

官方 wiki 列有：
- !mp timer <time>：一般倒數。
- !mp start [time]：立即或延後開始比賽。
- !mp aborttimer：停止一般倒數或開始倒數。

一般倒數與開始指令是分開的，Bot 需銜接流程。這些是官方指令定義，不代表已完成實機驗證；倒數、準備、開局與比賽結束事件格式及競態處理仍須實測。本文件未新增任何已驗證的 BanchoBot 回覆格式。

### 助理建議，待確認

| 階段 | 提早完成 | 倒數結束 |
| --- | --- | --- |
| 定位倒數 | 指定玩家到齊、隊伍正確後，取消倒數並設定第一張圖 | 重新核對；仍缺人或隊伍錯誤則暫停並告知 |
| 準備倒數 | 指定玩家全員準備後，取消倒數並開始 | 人員與隊伍仍正確則開始，不再等待準備 |
| 單張結束 | 設定下一張圖，重新進入準備倒數 | 不適用 |

- 同時收到全員準備與倒數結束時，只能開始一次。
- 反覆切換準備狀態不應無限重設總等待期限。
- 進入開始流程後不因準備事件重複排程；實際開始前的人員核對及異常分支仍待定。
- 最後未回答的問題：定位倒數結束仍缺人或站錯隊，是否暫停並交由發起者處理後再繼續？
- 各倒數時間、是否有短暫穩定準備時間，以及定位與選圖的精確切換時機尚未決定。

## 3. 模式二：addref 失敗的降級方向

使用者提出：若確實無法授予 referee，承載帳號仍可管理房間，明確告知使用者即可；比賽模式的額外需求後續再討論。

- 建房成功但 addref 失敗時保留房間，不自動關房。
- 明確區分「房間已建立」與「referee 授權已確認」，不可用訊息送出成功代替授權確認。
- 使用者仍可透過 Discord 指令，讓承載帳號代為管房。
- 一般遊戲內選圖與設定需另看 host 權限；進房、取得密碼與 referee 授權不可混為一談。
- addref 失敗發生頻率目前沒有實測資料，不判定為罕見。
- 是否重試、重試次數、是否提供人工補授權，以及自動轉移 host 均尚未定案。
- 先前提出「額外重試最多兩次」沒有獲得確認，不列為規則。
- /mp info 與 Discord DM／僅本人可見回覆曾因 invite 與 addref 混淆而討論，尚未形成新增功能決議。

關聯文件中的 referee 部分失敗補救仍是提案，本段為後續方向紀錄，不代表已正式取代該提案。

## 4. 關房公告與統一收尾

### 使用者提出的方向

- Discord 發起關房時，先在房間 IRC 聊天公告「幾秒後自動關房，請保存 mp link」。
- 若玩家已從 osu! 遊戲內手動關房，Discord 端先確認房況；已關閉就跳過關房並顯示訊息。

### 助理整理，待確認

Discord 請求關房 → 房間內公告關房時間與 mp link → 等待 → 核對房況 → 必要時送出關房 → 確認關閉 → 收尾一次。

| 核對結果 | 行為 |
| --- | --- |
| 確認已關閉 | 跳過關房指令，Discord 顯示房間已關閉 |
| 確認仍開啟 | 繼續關房流程 |
| 無法確認 | 顯示狀態待確認，不視為已關閉，不釋放名額 |

- 公告倒數期間若收到可信關閉確認，取消待執行的關房工作並收尾。
- 遊戲內與 Discord 同時關房，或收到重複事件，不能造成重複釋放名額／發布摘要。
- 如何查詢房況仍依關聯文件的待驗證訊號與證據規則；不能假設一定能即時查到，也不能僅憑 JOIN 失敗判定。
- 關房公告秒數、是否允許取消、比賽進行中如何處理關房，以及摘要內容與發布位置仍待討論。
- 公告文字只是產品文案提議，不是 BanchoBot 回覆格式。
